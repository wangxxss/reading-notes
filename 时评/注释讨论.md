
# 同事要把代码注释全删了，说“反正AI都能看懂”……

最近在团队里发生了一场争论。

起因是有位同事在提交代码时，把一段逻辑里的注释全删了。别人问他为什么，他理直气壮地说：“现在AI理解能力这么强，Cursor和Copilot扫一眼就知道这代码是干嘛的，还要注释干什么？写注释纯属浪费时间。”

更有人附和，甚至以自己“从写过一行注释”为荣，觉得这才是高级程序员的标配。

听起来似乎很有道理。毕竟现在把一段没见过的代码扔给AI，它确实能给你解释得明明白白。

但事实真的如此吗？**在AI时代，代码注释真的多余了吗？**

### 01 认清现实：AI能看懂“What”，却猜不透“Why”

那些主张“全删注释”的同事，其实混淆了一个核心概念：**AI擅长解释代码“在做什么”，却永远无法获知“为什么这样做”。**

举个例子，你看到一段代码：
```python
for user in users:
    process(user)
```

你问AI：“这段代码在干嘛？”
AI会秒答：“它在遍历用户列表并逐个处理。”

这没问题。但如果这段代码上面没有注释，无论是人还是AI，都不知道**为什么这里要用串行处理，而不是看起来更高效的并发处理？**

真实的原因可能是：
```python
# 这里必须串行处理，因为下游风控服务对单账户有并发限制。
# 如果改成并发，会触发风控导致账号冻结。历史Bug参考：#12345
for user in users:
    process(user)
```

AI不知道你们三个月前开过什么会，不知道产品经理有过什么特殊要求，不知道某个第三方库有个坑爹的遗留问题。**这些业务约束、历史包袱和架构取舍，是AI训练语料里根本不存在的“私有上下文”。**

硅谷有一篇被广泛引用的文章说得一针见血：**AI在恢复决策意图时格外薄弱，尤其是当那个意图涉及AI根本接触不到的约束时。**

### 02 反转：删掉注释，其实是在给AI“挖坑”

很多人觉得，既然AI能看懂代码，那留注释就是多余。但这恰恰忽略了一个最反直觉的现象：**在AI编程时代，注释不再是写给人看的说明书，而是写给AI看的“提示词”。**

我们来看看不写注释会发生什么。

假设你接手了一段没有任何注释的复杂代码，你让AI帮你“优化一下这段代码，提升性能”。

AI扫了一眼，觉得这里串行处理太傻了，于是“好心”地帮你改成了并发处理。结果上线没十分钟，下游风控系统报警，账号批量被封。

为什么会这样？因为没有注释告诉AI**“不能改什么”**和**“为什么不能改”**。

Google Chrome工程师Addy Osmani在分享AI工作流时专门强调：**“LLM是字面派，它们会按照指令来。用注释和规则来引导AI，给它详细的、有背景的指令。”**

一段带有清晰注释的代码，AI能在几百个Token里读懂它的完整语义和禁忌；而一段没注释的代码，AI要么靠猜，要么花大量Token去追踪调用链，最后还可能“自信地”给你挖个坑。

所以，删掉注释，不只是在为难接手的同事，更是在为难你每天用的AI工具。

### 03 注释分类指南：什么该删，什么必须留？

当然，同事的愤怒也不是完全没有道理。因为确实有很多“废话注释”在污染代码库。

比如这种：
```javascript
i++; // i加1
```

这种把代码翻译一遍的注释，确实该删，而且越早删越好。

在AI时代，我们需要做的不是“全删注释”，而是**把注释的角色从“代码翻译器”升级为“工程上下文的记录器”。**

我们可以把注释分为三类：

| 注释类型 | 例子 | AI能否替代 | 处理建议 |
|---------|------|-----------|---------|
| **What类**（翻译代码） | `i++; // i加1` | 能，AI解释得更好 | **果断删掉** |
| **Why类**（业务/历史约束） | `// 串行处理，因下游风控对单账户并发有限制` | **不能**，AI无此上下文 | **必须保留** |
| **Intent类**（给AI的指令） | `// 保持幂等，入参不可变，勿改并发模型` | 不能，是引导AI的信号 | **保留并精炼** |

真正的“好代码”，是变量命名能说清“What”，而把宝贵的注释位置留给那些AI和后人推断不出来的“Why”和“Intent”。

### 04 AI降低了写代码的成本，但没降低维护成本

GitClear曾分析了2020到2024年间的2.11亿行代码变更，得出了一个让人不安的结论：重构相关的改动从25%跌到了不足10%，而复制粘贴的代码比例从8.3%涨到了12.3%。

创始人Bill Harding给这个现象起了个名字：**“AI诱发的技术债”**。

因为AI写代码太快了，开发者粘贴代码的频率，甚至超过了重构和复用代码的频率。大家都在飞速地堆砌代码，却很少停下来留下上下文的记录。

“仓促添加的代码，对之后维护它的团队来说是有毒的。”

在代码库以前所未有的速度膨胀的当下，如果连注释也一并省略，最终的结果就是：**你的代码库会变成一个连AI都读不懂的“黑盒”。**

### 05 写在最后

其实，“以零注释为荣”往往是初级到中级开发者常犯的浪漫主义错误。随着工程经验的积累，踩过足够多因为没有注释而排查三天三夜的坑后，真正成熟的工程师会明白：

**好的注释不是对代码能力的妥协，而是对未来接盘者的善意，也是对自己记忆衰退的保险。**

AI能帮你写代码，但没有人能帮你写清楚你为什么要这样写。

下次再有同事说要删掉所有注释，你可以把这篇文章发给他。然后告诉他：删掉废话注释是好事，但删掉业务上下文，就是在制造下一代人（和下一代AI）都读不懂的代码垃圾。
