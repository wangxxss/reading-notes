# 让下游用最低成本的方式工作

*一种隐蔽的工程成本转嫁机制*

在国内不少十年龄期的前端项目中，可以观察到一个反工程直觉的现象：构建产物与源码一同存放于主 git 仓库。`build/` 目录下的压缩 JavaScript、几兆体积的 source map、被命名为「补提 dist 新版 hash chunk 产物」的 commit，构成了这类项目的常规景观。

任何稍具规范的工程团队都不会主动选择这种方案。git 不是制品库，不是 CDN。将构建产物纳入主仓的代价是直接的：版本管理被污染，代码审查失去意义，合并冲突频繁化，磁盘体积线性膨胀。

但这种方案并非无人懂得其错误才被采用。它是一种结构性后果。

追溯成因，往往可以定位到一个共同起点：项目立项的年代，运维侧不具备「持续集成」的能力。没有 Jenkins，没有 GitLab CI，没有 artifact registry。运维的工作方式停留在 shell 脚本时代：`git pull`，`rsync` 到 CDN 服务器。要求他们承接「拉源码、装依赖、跑 build、推产物」的完整流水线，超出了他们的工具栈与意愿。

于是这部分工作被下移到了开发侧。前端工程师在本地机器跑 build，把产物 commit 到 git，push 上去，运维只需 `pull` 即可拿到"成品"。git 在此被改造为一个被滥用的 artifact registry。

这个调整的本质是成本转嫁。

运维侧本应承担的「构建集成」工作，因能力或意愿缺失，被转移到了开发侧。表面上，运维的工作量降低了。整体上，组织为此付出的代价远高于节省的部分：仓库体积膨胀至 clone 一次需要数 GB，代码审查无法识别产物差异，源码与产物失同步导致的线上事故频发，新人 onboarding 需要数日才能理解产物提交的非显然约定。

这条转嫁链一旦形成，便难以拆除。整套发布流程都建构在其上：自研构建工具的设计前提是「git 中存在 hash 化产物」，运维的部署脚本硬编码了「从 git 拉 build 目录」的路径，测试环境从 git tag 直接部署。任何对 build 入 git 的修正，都会牵动整条发布链路的重新设计。这是一个典型的路径依赖陷阱。

这是一个技术现象。但同样的逻辑，在组织层面以同样的形式运作。

将「运维」替换为「测试」。测试团队的工作模式要求稳定、可重复、不依赖代码理解的用例。代价是开发侧被推动写入大量"测试友好"的代码：埋点、日志、注入点、mock 接口、testid 标记。代码体积膨胀，可读性下降，测试团队的 KPI 完成度提高。

将「测试」替换为「产品」。产品团队希望快速试错、随时调整需求、上线后仍可修改文案。代价是开发侧将所有元素做成可配置、可热更新、可灰度发布。架构复杂度提升数倍，产品团队获得了下午发出「换标题」指令、当晚即可上线的能力。

将「产品」替换为「业务」。业务方要求快速试水。开发侧承接了「先跑起来再说」的技术债。业务跑通后，管理层获得 KPI，技术债无人偿还。三年后业务收缩，团队解散，债务连同代码沉入档案库，等待下一任接手者将其挖出，归咎于前人草率。

每一环，下游均以最低成本的方式工作。每一环，节省的成本均堆积在开发侧。

这种格局的稳定性，源于一个结构性事实：开发的工作产出是最难量化的。

测试发现的 bug 可统计，产品上线的功能可统计，运维保障的可用性等级可统计。开发把代码写得让两年后仍可读、在评审中挡下糟糕设计、在 review 中发现并发隐患、重构掉一段会在半年后爆雷的代码，这些产出无法被汇报系统识别，向上呈报后管理层亦无法理解其含义。

唯一可汇报的事情是「修了几个 bug」。这构成了一个诡异的反馈环：写出 bug 的工程师与修复 bug 的工程师，是同一个人。在汇报系统中，他同时扮演消防员与纵火犯。管理层看到的是火被扑灭，而非火本可不烧起。

研发经理的 KPI 设计沿着同一逻辑展开：考核交付速度、缺陷率、加班时长。不考核员工保留率、技术债增量、团队幸福度。理性最大化之下，团队被视为可线性榨取的工时机器。「给压力第一名，谋福利倒数第一名」不是个体的道德缺陷，是 KPI 的结构产物。

回到 build 入 git 的案例。当年的决策者未必不懂工程规范。他可能只是被夹在「运维不肯学」与「业务等着上线」之间，做出了当时最小代价的选择。每个时间点的人都做了当时最小代价的选择，累积形成了今天的样态。这是结构层面的现象，不是个体层面的过失。

在一个成本结构已经定型的组织中，单个工程师能采取的行动有限。

其一，降低被转嫁的部分。在合理范围内拒绝越界请求，将可自动化的工作自动化，提供文档替代一对一答疑。这不是消极怠工，是将不应承担的成本退回原点。

其二，评估这条转嫁链是否值得继续承担。当前技能在外部市场的定价、承受压力与薪资的比值、下一个机会窗口的位置，这些是可量化的决策依据。当成本收益失衡时，离开比改造更经济。改造一个组织需要副总裁级的权力，单个工程师不具备杠杆。

中间路径，向上反馈、提改进方案、推动流程优化，在大多数情况下是低效的努力。问题不位于工程师所在的层级，工程师的所有改进尝试都会被结构吸收。

写代码的能力是工程师可以带走的资产。这是这类结构中，唯一稳定可持有的东西。
