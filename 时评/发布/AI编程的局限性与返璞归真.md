# AI编程的局限性与"返璞归真"

## 引言

AI编程时代，框架版本不兼容、代码不一定符合实际项目需求等问题日益突出。本文通过两个真实案例，探讨AI编程的局限性，以及为什么理解底层原理在AI时代反而更加重要。

---

## 一、核心观点：返璞归真

> AI越强大，你反而越需要理解底层原理，才能判断它写的代码能不能用。

---

## 二、AI编程暴露的真相

### 1. AI的知识是"平均值"，不是"精确值"

AI学过无数个项目，但它不知道：

- 你的项目用的是哪个版本
- 你团队有什么特殊约定
- 你刚升级了一个依赖，API已经变了

### 2. 框架越复杂，AI越容易"幻觉"

| 简单场景（AI很少错） | 复杂场景（AI经常错） |
|---------------------|---------------------|
| 写一个HTML表格 | Next.js 14 App Router vs Pages Router |
| 写一个CSS动画 | Vue 2和Vue 3的语法差异 |
| 写一个fetch请求 | Spring Boot 2.x和3.x的配置差异 |

### 3. 开发流程的转变

**以前的开发流程：**

```
思考 → 写代码 → 调试 → 完成
```

**现在的开发流程：**

```
描述需求 → AI生成代码 → 检查版本兼容性
→ 发现不对 → 手动改 → 再让AI改 → 又不对
→ 自己重写 → 完成
```

## 三、案例一：版本地狱

### 问题描述

```
AI训练数据的版本：
  React 16 → "用 class 组件"
  React 18 → "用 Hooks"
  React 19 → "用 Server Components"

你的项目版本：
  可能还在 React 17

结果：
  AI写的是 React 19 的代码
  你的项目跑的是 React 16
  一运行就报错 → 你还要花时间改
```

### 解决方案

**1. 在提示词中明确版本**

```
❌ "帮我写一个分页组件"
✅ "用 Vue 2.6 + Element UI 2.15 写一个分页组件，不要用Vue 3的Composition API"
```

**2. 建立项目上下文文件**

在项目中放一个 `tech-stack.md`，写清楚：

- React版本、Vue版本
- UI库版本
- 构建工具版本
- 特殊约定

**3. 让AI先分析再写**

```
"先看看我这段代码用的什么版本和API，然后再基于这个版本给我写新功能"
```

**4. 简单需求直接自己写**

改个按钮颜色、调个间距、加个判断逻辑——这种你自己30秒就写完了，让AI反而要花3分钟沟通和检查。

## 四、案例二：ThreadLocal上下文丢失

### 问题描述

用AI重构了一个调用微服务的功能：发邮件改成异步调用微服务。AI重构没问题，但调用服务化接口里面有个获取当前操作人的功能，数据写在ThreadLocal里。**同步调用没问题，异步调用就丢失了操作人信息。**

### 问题本质：AI看不到"运行时上下文"

```
AI看到的是：
  ✅ 调用邮件服务 → 改成异步 → 完美
  ✅ 代码逻辑 → 没有语法错误 → 完美

AI看不到的是：
  ❌ 这个服务内部依赖了 ThreadLocal
  ❌ ThreadLocal 是线程绑定的
  ❌ 异步线程 ≠ 请求线程
  ❌ 换了线程，上下文就丢了
```

这就像AI帮你把快递从"当面交"改成了"放快递柜"，但它不知道这个包裹需要**本人签收**。

### 为什么AI识别不出来？

**1. 跨服务/跨层的隐藏依赖**

```
你的调用链：
  Controller → Service → [异步] → MailService → 某个工具类 → ThreadLocal.get()

AI看到的只是：
  Controller → Service → [异步] → MailService

中间那个"某个工具类"里面悄悄用了ThreadLocal
AI根本不知道这个依赖链有多长、多深
```

**2. 运行时行为 vs 静态代码**

AI做的是"静态分析"——看代码结构。ThreadLocal是"运行时行为"——跟线程绑定。

静态分析看不出来：

- 这个请求经过了哪些拦截器
- 拦截器往ThreadLocal里放了什么
- 异步场景下线程池是怎么配置的
- 哪些Filter在请求链路中注入了上下文

**3. 企业架构的"隐性知识"**

企业项目里有很多"不成文的规定"：

- "我们所有接口都依赖SecurityContext.getCurrentUser()"
- "操作日志是通过ThreadLocal自动记录的"
- "数据权限过滤依赖当前用户ID"

这些知识：不在代码注释里，不在文档里，甚至可能连团队里的人都说不清楚。AI更不可能知道。

### 企业中常见的"隐形地雷"

| 隐藏依赖 | 同步OK | 异步出事 |
|---------|--------|---------|
| ThreadLocal用户信息 | ✅ 同一线程 | ❌ 丢失 |
| 事务上下文 @Transactional | ✅ 同一连接 | ❌ 新线程无事务 |
| RequestAttributes | ✅ 同一请求 | ❌ 跨线程丢失 |
| MDC日志链路追踪 | ✅ 同一线程 | ❌ traceId断了 |
| SecurityContext | ✅ 已认证 | ❌ 新线程未认证 |
| Locale国际化信息 | ✅ 正确语言 | ❌ 回退默认 |

### 解决方案

**方案一：手动传递上下文**

```java
// 在主线程获取
UserInfo user = ThreadLocalUserContext.getCurrentUser();

// 异步调用时传进去
CompletableFuture.runAsync(() -> {
    ThreadLocalUserContext.setUser(user);  // 手动设置
    try {
        mailService.sendEmail();           // 现在能拿到用户了
    } finally {
        ThreadLocalUserContext.clear();     // 记得清理！
    }
}, executor);
```

**方案二：用装饰器/包装器**

```java
// 更优雅的方式
asyncExecutor.execute(() ->
    new ContextTaskDecorator()
        .decorate(() -> mailService.sendEmail())
);
```

**方案三：改成消息队列**

如果业务上真的适合异步，直接发消息到MQ → 消费者从消息里拿用户信息，根本不依赖ThreadLocal。

## 五、AI时代的能力金字塔

### 以前的前端能力金字塔

```
        🥇 框架熟练度（会写React/Vue）
        🥈 工程化能力（Webpack/Vite配置）
        🥊 基础能力（HTML/CSS/JS）
```

### 现在的能力金字塔

```
        🥇 判断力（AI写的代码能不能用）
        🥈 基础功（理解底层原理才能排错）
        🥉 框架知识（让AI去记，你只需知道概念）
```

## 六、总结

### AI能做的事 vs 做不了的事

| AI能做的 | AI做不了的 |
|---------|-----------|
| 重构代码结构 | 理解ThreadLocal的运行时特性 |
| 改同步为异步 | 知道你们项目的隐性架构依赖 |
| 写Service层的调用逻辑 | 判断哪些改动会影响上下文传递 |
| | 预见异步场景下的"连锁反应" |

### 一句话总结

> **AI能写出逻辑正确的代码，但"逻辑正确"和"在你的架构中正确"是两回事。**

### 给开发者的建议

**1. 让AI先做架构分析**

```
"分析这段代码及其所有下游调用链，
 列出所有依赖ThreadLocal/RequestContext的地方，
 标注哪些在异步场景下可能丢失"
```

**2. 让AI给出风险评估**

```
"我要把这段同步调用改成异步，
 帮我评估可能出问题的点：
 1. 上下文传递
 2. 事务边界
 3. 异常处理
 4. 重试机制"
```

**3. AI写代码 + 人工审查**

```
AI写完 → 你重点检查上下文传递部分 → 测试 → 上线
```

### 最终结论

```
工具越来越智能
但人对技术的理解要越来越本质

不是不需要学框架了
而是要学框架背后的"为什么"

不是不需要写代码了
而是要知道"什么样的代码是对的"

AI是你的助手
但你才是那个拍板的人
```
