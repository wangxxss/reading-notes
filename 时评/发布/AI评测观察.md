# 我让 16 个 AI 写同一个弹窗，并用 Grep 数了数它们的细节

> 时间：2026-05-19
> 视角：资深 UI/UE 设计师 · 产品经理 · 前端开发工程师
> 评测对象：基于同一份需求、同一份 Prompt 的 16 份前端实现
> 评测方式：源码逐行核对 + 量化指标统计

## TL;DR

- **头部 9.50 vs 末位 6.62**，同一份需求下，"近乎可交付" 和 "需要返工" 之间存在 2.88 分鸿沟。
- 主弹窗 + 双子弹窗 + Toast 链路 **16/16 全员实现**——基础能力已普及。
- 但 **4/16 用 inline `onclick`**、**3/16 用 `Math.abs/Math.max(0,…)` 抹掉补差负数**、**2/16 偷懒用 `window.confirm`**、**仅 2/16 写了 `prefers-reduced-motion`**。
- 头部与中等的真正差距，不在"能写出来"，而在 **主动做没人要求的事**——加 ARIA、把 confirm 写成 Promise、把不可选行做成两行结构。

## 1. 起因

最近在做 AI 编程工具选型，想知道一个简单问题：
**给同一份需求、同一份 Prompt，主流 AI 编程工具产出的差距究竟有多大？**

需求选了一个真实业务场景——"政策优惠配置弹窗"。
有主弹窗、两个子弹窗、表格增删、统计联动、二次确认、Toast、不可选行、置灰按钮的 hover 三态文案。
不大不小，刚好覆盖一个企业级前端会遇到的多数交互模式。

Prompt 要求：HTML/CSS/JS 拆分三文件，科技风（深空蓝/冰蓝/银灰），响应式，详细注释。

样本一共 16 份。覆盖 8 个厂商：
Anthropic Claude Code、OpenAI Codex、字节 Doubao、DeepSeek、智谱 GLM、月之暗面 Kimi、MiniMax、阿里 Qwen。

**评测不靠运行截图，全部基于源码逐行核对**——截图永远展示作者最自信的那一帧，源码不会撒谎。

## 2. 评测方法

五个维度，加权总分：

| 维度 | 权重 | 关注点 |
|---|---|---|
| 需求完成度 | 30% | 表格 / 子弹窗 / 删除无确认 / 统计刷新 / 置灰按钮三态 hover / 二次确认 / Toast / 不可选行 ⚠️ / 添加后按钮变灰文案 |
| UI 视觉 | 25% | 科技风落地、配色、渐变、毛玻璃、阴影、字体层级 |
| 交互细节 | 20% | 微动、过渡、自定义弹窗、Toast 实现、按钮反馈 |
| 代码质量 | 15% | 模块化、CSS 变量、XSS 防护、是否 inline onclick、注释 |
| 响应式 | 10% | 三档断点、表格自适应、子弹窗适配 |

满分 10 分。等级 S（≥9.0）/ A（8.0~9.0）/ B（7.0~8.0）/ C（6.0~7.0）。

## 4. 量化数据：AI 在哪儿集体做对 / 没做对

这一节是这次研究里最有意思的部分。
用 `grep` 把 16 份产出的关键代码模式都数了一遍，得到下面这张表：

| 指标 | 命中率 | 含义 |
|---|:---:|---|
| 主弹窗 + 双子弹窗 + Toast 链路 | **16 / 16** ✅ | 基础能力已是 AI 标配 |
| 定义 CSS 变量令牌 | 15 / 16 | 现代 CSS 写法已普及（变量数从 23 到 55） |
| XSS 防护（escapeHtml / textContent） | 14 / 16 | 多数模型主动转义 HTML |
| 自定义二次确认（非原生 confirm） | **14 / 16** | 2 份偷懒用了 `window.confirm` |
| 不可选行 ⚠️ + 原因 + ---  三联到位 | ~13 / 16 | 极少数把这三件事全做了 |
| 三档媒体查询断点 | 6 / 16 | 多数停在两档断点（768/480） |
| 严格命中"已在政策产品列表中" 文案 | **6 / 16** ⚠️ | 一半模型把它改成"已添加" |
| IIFE 严格封装 | **4 / 16** | 多数模型把变量裸放在顶层 |
| inline onclick 反模式 | **4 / 16** ❌ | 命名空间污染，每个目录都用了 4 次 |
| Math.abs / Math.max(0,…) 抹掉补差 | **3 / 16** ❌ | 丢失负数语义 |
| role="dialog" + aria-modal | **3 / 16** | 多数模型不主动加 ARIA |
| prefers-reduced-motion 无障碍 | **2 / 16** | 几乎没人想到这件事 |

这张表比任何定性描述都有冲击力。
**基础链路 16/16**，但 **真正考验细节意识的指标，命中率经常掉到个位数。**

> 越是基础的"能跑"，越是普世；越是细节的"扣得准"，越是稀缺。
> 这是当下 AI 编程工具横评最朴素的结论。

## 5. 四个反直觉发现

### 5.1 同厂商版本号不是单调上升

这是最让我意外的一条。

- **Doubao 1.0 (6.74) > Doubao 2.0 (6.62)**
- **MiniMax 2.5 (7.66) > MiniMax 2.7 (7.16)**

Doubao 2.0 视觉上明显比 1.0 好（CSS 变量更完备、加了双层 radial glow、标题渐变文字）。
但 JS 端反而退化：`onclick="fn(id)"` 内联挂 window，全局污染，需求文案细节也出现遗漏。

MiniMax 2.7 也类似——加了事件委托是进步，但搞了一堆 emoji 图标（📦🛒🗑⚠️）放进"科技风弹窗"，移动端还直接隐藏了金额列，造成关键信息丢失。

**版本号迭代并不等于全面进步。** 视觉与工程经常此消彼长。

### 5.2 同工具不同模型，差距约 1 分

样本里有两个 Claude Code 产出——同样是 Anthropic 的 CLI 工具，一个由 Opus 4.7 驱动，一个由 Kimi 驱动。

- Claude Code · Opus 4.7 → 9.50
- Claude Code · Kimi → 8.59

差距 **0.91 分**。

Kimi 版本视觉资产堆叠很到位：aurora 光晕、网格遮罩、移动端底部抽屉，是张扬的"科技风"。
但在需求条款的精读上有几处偏差——表格"固定高度内部滚动"没实现、不可选行金额硬编码 `---` 与"0 显示 -"规则混用、补差额度用 `Math.max(0, …)` 抹掉负值、还留了一个 `debounce` 工具函数定义后从未使用。

Opus 版本更稳。视觉没有那么张扬，但需求边界处理、无障碍意识（`prefers-reduced-motion`、`role=alertdialog`）、不留死代码这些细节全都到位。

**同样的工具链，模型不同，输出质量可以差出一个等级。**

### 5.3 OpenAI 与 Anthropic 同台，相差 1.43 分

这一轮加入了 OpenAI Codex 的产出，正好和 Claude Code Opus 形成同台对照——两家美国头部 AI 实验室的 CLI 编程工具，跑同一份 Prompt。

- **Claude Code · Opus** → 9.50（S 档第一）
- **OpenAI Codex** → 8.07（A 档第九）

差距 **1.43 分**。

Codex 不是"差"。它的代码组织反而比榜单上多数产出都更克制：纯函数 render、`replaceChildren` 性能合理、模块分层 `data → state → dom → render → bindEvents` 干净利落、CSS 变量体系扎实。读这份代码会有种"老派 OpenAI 工程范"的感觉——没有冗余封装、注释言简意赅。

但它在 **产品打磨** 这一环输得很彻底。二次确认直接 `window.confirm('确认提交政策优惠配置？')`——浏览器原生灰白色对话框，把精心搭建的科技风视觉砸了个稀碎。Toast 用 setTimeout 改 inline style 淡出，没声明 transition，动画断裂。候选表"提示"独立成列，没按原型贴到产品名下方。

**Codex 的工程感强，产品感欠半步。** 而 Claude Code Opus 在工程感同等的基础上，多走了那半步——把每一个细节都掰扯到位。

> 当两个工具的"基础工程能力"已经接近天花板时，差距就转移到"产品打磨深度"上。这是一个很有意思的趋势——以后比拼的不再是"能不能写出来"，而是"能不能把每个边角细节都打磨到位"。

### 5.4 视觉天花板与工程标杆，往往不在同一份产出上

GLM 系列在这点上特别明显。

- GLM 5V → 9.00：粒子效果 + 网格 + 脉冲徽章，视觉冲击力最强
- GLM 5.1 → 9.00：IIFE + 事件委托 + escapeHtml + 三档 tooltip 全员命中，是工程规范的标杆
- GLM 5 → 8.66：视觉天花板最高（深空蓝表头 + 等宽数字 + 双光球 + 网格底纹），但被 `Math.abs(diff)` 把负补差显示成正值的逻辑 bug 拉下 S 档

要美术，选 5V。
要工程规范，选 5.1。
要最像"科技控制台"的视觉，选 5。
**三者拿到一起反而是个套餐——可见一个 AI 的实现，永远在 "炫" 和 "稳" 之间做取舍。**

## 6. 四个共性失误（含真实代码对比）

### 6.1 失误一：精确文案落地——"已在政策产品列表中" 命中率仅 6/16

需求里写得清清楚楚的一句话——
"添加后按钮变灰，显示『已在政策产品列表中』"

**只有 6 / 16 严格命中**。剩下的写成了"已添加"、"✓ 已添加"，或者直接把按钮 disabled 不动文案。

**正例：claudeCode-opus** （`script.js:261`）

```js
const btnText = inList ? '已在政策产品列表中' : '+ 添加';
```

需求原文照抄，分支清晰。

**反例：traeCN-doubao**（`script.js:167`）

```js
${isAvailable ? '+ 添加' : '已添加'}
```

简化成了两个字。AI 觉得 "已添加" 是 "已在政策产品列表中" 的合理同义词——但产品经理写这种长文案，**正是为了让用户清晰知道"这条已经在哪个列表里"**。AI 抹掉了语义细节。

这不是 AI "不会写"，是 **AI 在长 Prompt 里对具体文案的注意力会被周边大量描述稀释**。
越是埋在交互细节里的具体文案、越是只出现一次的关键短语，越容易被改写成 "差不多意思" 的版本。

放到生产场景，这意味着：**你写的需求文档里那个咬文嚼字的产品文案，很可能在 AI 那里变成"近义词"。** 这是需要后置 review 把守的事，不能信任。

### 6.2 失误二：负数语义被抹掉——3/16 用 Math.abs 或 Math.max(0,…)

"核销补差额度 > 0 时显示红字"——这是需求原文。
潜台词是：补差可以为负（核销 < 优惠），可以为零，可以为正，**只有正数时才标红**。

Grep 全部 16 份，**3 个产出干脆把负数抹了**：

```js
// claudeCode-kimi/script.js:391
const diff = Math.max(0, writeOff - totalDiscount);

// traeCN-kimi2.5/script.js:329
const diffAmount = Math.max(0, verifyAmount - totalDiscount);

// traeCN-glm5/script.js:334
DOM.statDifference.textContent = formatAmount(Math.abs(difference));
```

表面看，没违反 "> 0 红字" 的字面要求。
但实际上，当 "核销额度 < 优惠额度" 时（业务上完全可能），AI 把负数抹成了 0 或正数，丢失了 **"核销不足以覆盖优惠" 这个最关键的业务语义**。

**AI 倾向于"防御性"地把数字弄到非负，因为它觉得"负数看起来像 bug"。**
但这恰恰是这个业务的真实状态。

这是个比文案偏差更隐蔽的风险——**文案错了一眼看得出，逻辑错了要业务跑起来才暴露。**

### 6.3 失误三：偷懒用原生 API——2/16 用了 window.confirm

需求要求"弹出二次确认框，确认后 Toast 提示成功"。
潜台词是：自定义弹窗、自定义 Toast，要与整体科技风视觉一致。

但有两份产出直接偷懒用了原生 API：

```js
// codex/script.js:267
if (window.confirm("确认提交政策优惠配置？")) {
  showToast("政策优惠配置成功");

// traeCN-ds4f/script.js:486
var confirmed = window.confirm('确认提交政策优惠配置？')
```

浏览器原生灰白色对话框，硬生生破坏了精心搭建的暗色科技风。

**MiniMax 2.5、Doubao** 系列则用了原生 `title` 属性做 hover 提示——纯文本气泡，反应延迟 1.5 秒，连样式都不能改。

特别有意思的是 Codex 这个例子：它在其他维度上工程感很强（CSS 变量、模块分层、事件委托），却在二次确认这一环偷了懒。
**这说明"偷懒"不是能力问题，是注意力分配问题**——当模型把精力花在搭建骨架时，可能就顾不上"每一个交互细节都要自定义"这种产品级要求了。

对比下面这份"不偷懒"的反面教材：

```js
// traeCN-glm5v/app.js
const confirmDialog = $('#confirmDialog');
const confirmMessage = $('#confirmMessage');
// 完整的 showConfirm Promise 化实现，调用方写 await showConfirm(...)
```

差距是 8 行 vs 1 行，但视觉一致性差一个档次。

### 6.4 失误四：浅色弹窗当成"科技风"

Prompt 写了 "深空蓝、浅冰蓝、银灰"。
至少 4 份产出，**入口或外围确实是深色**，但点开主弹窗一看，**内部是 `rgba(255, 255, 255, 0.95)` 的白底**——一个浅色 Material Design 风格的对话框，被强行套在深色背景上。

**最离谱的是 Qwen 3.6**——它的 CSS 里有这样一行：

```css
/* traeCN-qwen3.6/project/css/styles.css:13 */
--color-accent-blue-end: #764BA2;    /* 科技蓝渐变结束 */

/* :70 */
background: linear-gradient(135deg, #667EEA 0%, #764BA2 100%);
```

**注释里写着"科技蓝渐变"，但 `#764BA2` 是个紫色**。
这是 Bootstrap 5 文档首页的默认配色（`#667EEA → #764BA2` 紫蓝渐变），是 2020 年前后 SaaS 落地页的样板间。
AI 模型把它的颜色起名为"科技蓝"，却完全没意识到自己填了个紫色——**它认知里"现代科技感"和"紫蓝渐变"几乎是绑定的**。

视觉气质这件事，**Prompt 里写多少形容词都不够**。AI 没有"色彩感"，它只能从训练数据里调用最常见的几套配色。说 "科技风"，它最容易给的就是 "Hero 大图 + 渐变 CTA + 卡片阴影"——SaaS 落地页的样板间。

如果你想要真正的"深空蓝"，唯一靠谱的办法是 **在 Prompt 里直接给十六进制色值**。

## 7. 几个不像 AI 的瞬间

挑几个让我眼前一亮的瞬间——这些细节没有一个是 Prompt 强制要求的，是模型"自己觉得应该做"的。

### 7.1 Claude Code Opus 主动加 ARIA + reduced-motion

```html
<!-- claudeCode-opus/index.html:90 -->
<div id="configModal" class="modal" role="dialog" aria-modal="true" aria-labelledby="configModalTitle" hidden>

<!-- :308 -->
<div id="confirmDialog" class="modal modal--confirm" role="alertdialog" aria-modal="true" hidden>
```

```css
/* claudeCode-opus/styles.css:1110 */
@media (prefers-reduced-motion: reduce) {
```

**4 个弹窗全部带 `role + aria-modal`，确认框用了语义更准确的 `alertdialog`**。
对动画敏感的用户（前庭功能障碍、眩晕病患者）会受益于 `prefers-reduced-motion` 这条媒体查询。

Prompt 里**没人**要求做无障碍。但 Opus 做了。
而其他 15 份里，只有 Qwen 3.5 多写了一行 `prefers-reduced-motion`，3 份写了 `role=dialog`。

### 7.2 GLM 5V 把 confirm 写成 Promise

```js
// traeCN-glm5v/app.js
async function handleConfirm() {
  const ok = await showConfirm('确认提交政策优惠配置？');
  if (ok) showToast('政策优惠配置成功');
}
```

`showConfirm` 返回 Promise，调用方 `await` 即可。这是现代 JS 的标准模式。
对比 codex / ds4f 用 `window.confirm` 阻塞式调用——同样一行代码，一份是 2026 年的写法，一份是 2010 年的写法。

### 7.3 DeepSeek V4 用两行结构处理不可选行

`<tr>` 里硬塞 `⚠️` 文字会挤压列宽。
DS V4 把不可选行处理成 "主行 + 提示行 colspan=4" 两行结构——产品名占一行、警告占下面一行、视觉上没有任何拥挤。

这是一个**懂表格语义**的细节。多数 AI 会把 `⚠️` 塞进操作列或单独加一个"提示"列，前者拥挤，后者破坏表格结构。

### 7.4 Qwen 3.5 业务弹窗外包了一层"管理平台外壳"

它在业务弹窗外做了一个**侧边导航 + 面包屑 + 卡片**的管理平台外壳页。
Prompt 里只要求"弹窗"，没要求"管理平台"。
但 Qwen 3.5 主动给了一个**完整的业务场景**——一下子从"孤零零的弹窗 demo"变成了"真实的后台系统截图"。

### 7.5 Kimi 2.6 移动端改成"底部抽屉"

它的移动端不是简单缩小弹窗，而是改成了"从底部滑出的抽屉"——这是 iOS Action Sheet 的模式。
懂的人才会这么做。

---

**这五个细节，没有一个是 Prompt 强制要求的。**
**它们是模型"自己觉得应该做"的。**
**这些"自觉"，才是顶级 AI 编程工具与中等之间真正的鸿沟。**

## 8. 给三类人的建议

### 8.1 如果你是选 AI 编程工具的人

| 场景 | 推荐 |
|---|---|
| 要 SOTA 体验、对质量近乎苛刻 | **Claude Code Opus** —— 降维打击 |
| 国产首选、视觉与工程都要 | **Kimi 2.6** / **GLM 5.1** / **GLM 5V** —— 都 ≥9.0 |
| 性价比 | **DeepSeek V4** —— 9.10 第三名 |
| 工程为主、不太需要 UI 演示 | **OpenAI Codex** —— 代码克制干净，但产品打磨欠半步 |
| 避坑 | Doubao 系 / MiniMax 2.7 / Kimi 2.5 |

### 8.2 如果你在写 Prompt

- **关键文案要重复强调**。把"已在政策产品列表中"这种短语放进 Prompt 多次，并标注 "原文照抄不要近义改写"。
- **边界值要列举**。"当 X 为负时应该 Y" 比单纯说 "Y 时 Z" 有效得多——AI 不会替你脑补反向场景。
- **明确禁止偷懒方案**。直接写出 "不要使用 `window.confirm` / `alert` / `title` 属性"。
- **指定具体颜色比形容词更有效**。"科技风" 不如 `#0b1530 → #4ea1ff` 这样直接给色值——否则 AI 会给你 `#667EEA → #764BA2` 的 Bootstrap 紫蓝渐变。
- **无障碍要写出来**。"添加 `role=dialog / aria-modal / prefers-reduced-motion`" —— 不主动要求，多数模型不会做。

### 8.3 如果你在 review AI 产出

用 grep 跑这几条快速识别"AI 偷懒模式"：

```bash
# 是否用了原生 confirm
grep -rn "window.confirm" .

# 是否抹掉了补差负数
grep -rnE "Math\.abs|Math\.max\s*\(\s*0" .

# 是否 inline onclick
grep -rn 'onclick="' .

# 是否严格命中需求文案
grep -rn "已在政策产品列表中" .

# 是否做了无障碍
grep -rn "prefers-reduced-motion\|role=\"dialog\"\|aria-modal" .
```

5 行 grep 比通读 1500 行代码快得多。
**截图永远展示作者最自信的那一帧；代码不会撒谎。**

## 一句话总结

**AI 编程工具的差距，不在于 "能不能写出来"，而在于 "细节能不能扣到位"。**

16 份产出全部完成了主弹窗 + 双子弹窗 + 二次确认 + Toast 的基本链路。
但只有 6 份能把"已在政策产品列表中"这一行文案抄对。
只有 4 份做了 IIFE 工程封装。
只有 2 份主动加了无障碍 ARIA。
只有 1 份在 5 个维度上同时拿到 9.3+。

> 越是基础的"能跑"，越是普世；越是细节的"扣得准"，越是稀缺。
> 头部模型与中等模型的真正分水岭，是 **主动做没人要求的事**。
> 这就是当下 AI 编程工具横评最朴素的结论。
