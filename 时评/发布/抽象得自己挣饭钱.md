# 我花一天重构一坨屎山,悟出一句话:抽象得自己挣饭钱

那天我接手一段跑了五年的代码,一千二百行,越读越想骂人。

最离谱的是这么一处——有人为了在一行日志里算个附件总大小,手搓了三层封装:一个跟 JDK 自带重名的函数式接口,一个静态 `reduce` 方法,外加一个静态"求和器"对象。

一个 for 循环的事:

```java
// 它要做的:
long total = 0;
for (var a : attachments) total += a.length;

// 它写成的:自造接口 + reduce + SUMMER,三层
```

我当时就一个念头:这不纯纯炫技吗?

类似的还有一堆:有 lambda 的年代,满屏 Guava 匿名内部类;一个抽象基类,翻遍整个项目只有一个子类——抽象了个寂寞;布尔判断靠运算符优先级硬凑,`a && b || c`,下一个人得盯半天才敢动手。

"瞎几把写"三个字到嘴边了。

但打脸来得很快。

## 同一天,我自己写的另一段,却被夸"结构清晰"

巧了,当天我又翻到几年前自己写的一个广告模块。三十多种广告类型,一种一个实现类,一个门面在启动时建好"类型→处理器"的映射,按产品自动分发。新增一种广告?二十二行,只声明一下"我是哪种类型",剩下的基类和接口默认实现全给你兜住。

这模块用了策略模式、门面、接口隔离——一点都不"简单直接",全是抽象和结构。

这下就尴尬了:同样是抽象,凭啥我这段是"结构清晰",前面那段是"过度设计"?要是"别搞那些花里胡哨的、按业务直接写"是对的,那我这个用了一堆模式的,不也该挨骂?

我盯着这两段代码看了半天,突然想通了。

## 好代码的标准:不是简单,也不是高级

我过去那句口头禅——"别搞那么多乱七八糟的,直接写"——只对了一半。

要是把它当真,理解成"别抽象、平铺直叙地写",那写出来的,恰恰就是那坨一千二百行、复制粘贴、`Map<String,Object>` 满天飞的大泥球。业务一长,它自己就烂成一团。

真正的分界线,既不是"简单还是复杂",也不是"用没用设计模式",而是:复杂度,得对得上问题本身的复杂度。

拿这把尺子一量,全清楚了:

- 一个子类还套抽象基类、为一行日志手搓 reduce——问题没那么复杂,你凭空造复杂度。该骂。
- 三十种广告类型用策略模式分发——复杂度是真实存在的,抽象刚好接住了。该夸。
- 三十种类型硬塞进一个巨型 if-else"直接写"——把真实的复杂度硬压扁,也是坑,换了个姿势的烂而已。

所以你讨厌的从来不是"抽象"或"技巧",而是对不上号的抽象:既包括无中生有的炫技,也包括业务都复杂了还要硬平铺。

抽象得自己挣饭钱。挣不到的,一行都嫌多;挣得到的,该上就上。

## 顺手再骂一个:用异常类型搞国际化

说到过度设计,还有个反向典型——异常。

我那项目的异常是散养的:几乎每一种错误,都单独定义一个异常类。我猜当初是想搞国际化,让每个异常自带一种语言文案。结果呢?

调用方要么 `throws` 一长串,要么层层 catch 再包一层,原始堆栈埋得干干净净。定位一个 bug,得在七八个异常类之间反复横跳。加一种错就加一个类,异常包持续膨胀。

这是个经典的错位:异常的"类型",该用来说"出了啥问题、上层怎么处理",不是用来说"显示成哪国语言"的。国际化是"错误码 + 文案表"的活儿,跟异常类层次八竿子打不着。两件事一耦合,就逼出了"一个文案一个类"的灾难。

正确做法朴素得多:一个不受检的统一业务异常,带个 `code`。`code` 去查文案表做国际化,类型就一个,上层在边界统一捕获,定位靠 `code` 加堆栈,一步到位。

国际化是真问题,"每个错误一个异常类"是对不上号的、过度的解法。

## 最扎心的问题:他们是故意写得让你看不懂吗?

聊到这,绕不开一个更阴暗的猜测:会不会有人故意把代码写烂,让自己"不可替代"?

这种人是有的,业内叫"屎山自保"。但我越想越觉得:这是少数,而且多半是你想多了。

能用"水平、习惯、赶工"解释的,就别先往恶意上想。大多数烂代码的真相是:学会个花活逮哪用哪(金锤子);想显得聪明、刷存在感(那是写给自己爽的,不是为了坑你);从别处抄来照搬;多人接力打补丁没人收拾。这些指向的都是"没想那么多",不是"精心设计让你看不懂"。

故意混淆其实是个蠢策略。真要写得别人看不懂、还能跑、还能过评审,比写清楚难多了,没人闲到这份上。而且它反噬:你把自己焊死在那个模块上,换组、晋升、休假都难,成了"只能修 bug 的人",而不是"能干大事的人"。真有本事的人根本不靠这个保命——他们的价值在"能解决新问题",不在"垄断旧屎山"。

还有个问题:"他是不是故意坑我"这个滤镜本身就有害。它几乎总是错的,还毒化协作——你一旦这么想,就懒得理解、懒得改,反而把屎山养得更肥。

烂代码其实是"没有评审文化 + 没有统一规范"的系统性产物,跟写的人坏不坏没关系。

有 code review,那个自造 reduce 第一次提交就被打回了;有异常规范,就不会有满地散养的异常类。没人拦,烂写法就活下来了。就这么简单。

## 最后

一天的重构加吵架,我有个核心判断:好代码的标准不是"简单",也不是"高级",是复杂度匹配。抽象得自己挣饭钱。

还有一个发现:过度设计和过度平铺,是同一枚硬币的两面——都是因为没看清问题到底有多复杂。

再有就是:别花精力猜同事写烂代码的动机,去推 code review 和统一规范。管用得多。

所以别记"别搞那些乱七八糟的"这句话了。记住另一句就够了:该简单的地方坚决简单,该抽象的地方老实抽象。

能不能做到这一步,才是分开"瞎几把写"和"真有水平"的界线。
