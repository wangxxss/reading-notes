# 那套优雅的设计,我盯着看了半小时,才发现它从没运行过

> 一次老代码考古,和一个关于"会写"与"该写"的故事。

## 一、越看越佩服,直到我发现一件事

前几天翻一个几年前的模块,读到一个 DTO,第一眼有点惊艳。

它不是普通的"一堆 getter/setter"。它 `implements Iterable`,还配了一套自己手写的 `compose` 方法——把好几个可迭代对象惰性地拼成一条流,内部是嵌套的匿名 `Iterator`、手动维护游标,泛型签名里还老练地用了 `List<? extends Iterable<T>>`。

我心想:这人有点东西啊。一个搜索结果对象,能直接 `for-each` 出里面所有产品的"可预订数量",设计上是把整棵结果树抽象成了一个可遍历的序列。挺漂亮。

然后我做了一件所有考古者都该做的事:**搜一下,谁在调用它。**

搜索结果是——没有人。

整套 `Iterable` 也好、`compose` 也好,唯一的调用点,是这些类**自己内部互相调用**。真正用到那批数据的业务代码,走的是最朴素的 `getXxxList()` 字段 + 对象拷贝,跟这套优雅机制一点关系都没有。

我盯着那半屏"精巧"看了半小时,才反应过来:**它从来没被通上电。**

## 二、代码考古:一层层剥开

越挖越有意思。

**第一层:它是复制来的。** 这套设计在领域层(内部模型)和 DTO 层(对外传输)各有一份,类名一一对应,连那段手写迭代器都**逐字相同**。显然是先在领域层设计好,再整套镜像复制成对外 DTO——连"可迭代"这种行为都顺手搬了过来,复制时没人问一句"DTO 需要能迭代吗"。

**第二层:它是个半成品。** 顺着继承链往下看,叶子节点的抽象类也郑重声明了 `implements Iterable`,却**根本没实现 `iterator()`**;某个业务分支的子类同样没实现。只有主干上的两个类补齐了。也就是说,作者摆好了接口契约,打算让子类"逐个补齐",然后……补到一半就停了。

**第三层,也是最要命的一层:里面藏着一个从没被发现的 bug。**

那个手写的 `compose`,大意长这样:

```java
// 把多个 Iterable 拼成一个,惰性遍历
int index = 0;
Iterator<T> curr = null;

public boolean hasNext() {
    if (index >= iterables.length) return false;
    while (curr == null || !curr.hasNext()) {
        ++index;                        // ← 第一次进来 curr==null,直接就 ++
        if (index >= iterables.length) return false;
        curr = iterables[index].iterator();
    }
    return true;
}
```

发现了吗?第一次调用时 `curr == null`,进了循环立刻 `++index`,`index` 从 0 变成 1——**第 0 个元素被直接跳过了**。按它的实际拼法,被吞掉的恰好是"推荐结果"那一整块。

一个会静默丢数据的 bug,在代码里躺了好几年。

而它之所以从没炸过,原因很简单也很扎心:**没有人真正跑过它。** 真跑过,结果早就对不上,早就被发现了。这个"沉睡的 bug",反而成了"这段代码是死代码"最硬的证据。

## 三、为什么"聪明人"反而容易写出这种代码

这里我想说清楚一点:写这段代码的人,**技术不差**。

能手写惰性迭代器、会用泛型通配符、有把结果树统一抽象成序列的意识——这些都不是新手能做到的。恰恰相反,这是一个有技术热情、读过进阶资料、"想写点不平庸的代码"的人才会留下的痕迹。

问题也正出在这儿。这类代码有一个共同的心理配方:

- **手里有锤子,看什么都像钉子。** 刚掌握一个漂亮的招式,会忍不住找地方用出来,哪怕业务根本没要求。
- **"以后可能有用"的错觉。** 为一个想象中的需求提前铺抽象,结果那个需求永远没来。
- **不知道标准库早有现成的。** 这套 `compose`,`Stream.flatMap` 或 Guava 的 `Iterables.concat` 一行就能替代——而且不会写错边界。自己造轮子,还造出了 bug。
- **有热情起头,没纪律收尾。** 接口摆得很宏大,实现却虎头蛇尾;更没有测试去兜底。

一句话:**他掌握了"招式",但还没掌握"什么时候不该出招"。**

## 四、真正的成熟,是做减法

我们太容易把"会写复杂的东西"当成技术强。但在工程里,判断往往是反过来的:

> **技术的成熟,不体现在你能写出多精巧的抽象,而体现在你知道有多少抽象根本不该写。**

几条我自己反复提醒自己、也想留给团队的原则:

1. **YAGNI(You Aren't Gonna Need It)。** 没有当下的调用方,就不要为"可能"建抽象。没通电的抽象不是资产,是负债——它要被阅读、被维护、被绕过,还会误导后来人照着复制一遍。

2. **先问"标准库/成熟工具有没有"。** 你想手写的那个巧妙工具,大概率前人写过、测过、修过 bug 了。自己造轮子的默认答案应该是"不造"。

3. **数据是数据,行为是行为。** 让一个 DTO 去实现集合迭代语义,是把两件不该耦合的事捆在了一起。边界清楚,后面才不会长歪。

4. **没有测试的"精巧",等于没写。** 那个躺了几年的 off-by-one,一个单元测试就能当场抓住。手写的越"聪明",越需要测试来证明它真的对。

5. **Code Review 不是找茬,是"通电测试"。** Review 时多问一句"谁会调用它",很多过度设计当场就现形了。

## 五、最后

回到那段代码。我最终的处理很简单:确认无人调用后,把 `Iterable`、`compose`、那半截 `iterator()` 全删掉,还原成一个干净的、纯粹的数据对象。删掉的那一刻,模块反而清爽了。

这不是在嘲笑谁——**这种代码我自己年轻时也写过一堆**,那种"我要写点高级的"的冲动,几乎是每个程序员成长路上的必经之路。会招式是天赋,收得住招式才是功夫。

写得复杂,是本能;
写得简单,是修行。

共勉。
